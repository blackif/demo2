# Issue 执行规范

本文件是 AI 执行 GitHub Issue（由 `check_document` Action 自动创建）时必须遵守的规范。
Issue 的具体任务内容（如生成 readme）由 Issue 正文「要求」中引用的 skill 规定，本文件只规定 **如何判断能否执行、如何执行、如何收尾**。

## 1. 目的与范围

- 目的：让 AI 正确地接手并完成一个指定的 Issue，并把结果准确地反映到 Issue 上。
- 一次只处理用户指定的那一个 Issue（编号由用户给出），不自行挑选或批量处理其他 Issue。
- 不做：修改 Issue 标题；关闭 Issue（除非用户另行要求）；处理 Issue 正文「要求」范围之外的文件。

## 2. 输入

| 项目 | 内容 |
|---|---|
| 输入 | 仓库（如 `blackif/demo2`）与 Issue 编号 |
| Issue 结构 | `## 任务`、`## 要求`、`## 验收条件`（模板：`sap/document/template/issues.md`） |
| 标签 | `Todo`（待处理）、`Done`（已完成），大小写须完全一致 |

调用示例：「按 sap/document/skills/issue_execution.md，执行 blackif/demo2 的 Issue#2」。

## 3. 工具使用

- 读取与修改 Issue 使用 **REST API**（`gh api repos/{owner}/{repo}/issues/{n} ...`）。GraphQL 在 Claude Code 会话中不可用，`gh issue view` / `gh issue edit` 可能因此失败。
- 修改 Issue 前，先重新读取最新状态，避免覆盖他人的改动。

## 4. 执行流程

### 步骤 1：检查 Issue 状态（前置检查）

读取 Issue，依次检查，**任何一项不满足都不得执行，也不得修改 Issue**：

| 检查项 | 条件 | 不满足时返回的消息 |
|---|---|---|
| 状态 | `state` 为 `open` | 「Issue#N 的状态不是 Open，AI 不能执行此 Issue。」 |
| 标签 | `labels` 包含 `Todo` | 「Issue#N 缺少 Todo 标签，必须存在 Todo 标签，否则 AI 不能执行此 Issue。」 |
| 重复执行 | 不含 `Done` 标签 | 「Issue#N 已带有 Done 标签，请确认是否需要重新执行。」 |

### 步骤 2：理解 Issue

1. 阅读 `## 任务`、`## 要求`、`## 验收条件` 三个部分。
2. 打开「要求」中引用的 skill 和目标目录，完整阅读 skill。
3. 判断是否可以执行。出现以下任一情形，视为**无法执行或有疑问**：
   - 任务、要求或验收条件的含义不明确，或相互矛盾。
   - 引用的 skill 或目标目录不存在、不可读。
   - Issue 要求的内容与引用 skill 的规定冲突。
   - 执行需要 AI 不具备的条件（如需连接 SAP 系统、需要人的业务判断）。
   - 任务超出「要求」中写明的范围。

### 步骤 3：无法执行或有疑问时 → 跳过

1. **跳过此 Issue**：不执行任何任务、不创建或修改目标文件。
2. **不修改 Issue**：不勾选 checkbox，不增删标签（保持 `Todo`），不关闭。
3. **返回消息**给用户，包含：
   - Issue 编号和标题。
   - 跳过的原因（具体指出是哪一条要求不明确、哪个文件缺失等）。
   - 需要用户确认或补充什么，才能继续执行。

### 步骤 4：可以执行 → 执行任务

1. 严格按「要求」和其引用的 skill 完成任务（例如 readme 类 Issue 按 `readme_generation.md`，包括其中的自检与报告）。
2. 只在「要求」指定的路径下创建或修改文件；目标目录不存在时按要求先创建。
3. 执行过程中途发现无法继续或出现疑问，回到**步骤 3**，并保证不留下半成品（已创建的文件需向用户说明）。

### 步骤 5：逐条核对验收条件

对 `## 验收条件` 中的**每一条**，用实际结果核对（打开文件、确认路径、运行校验），不凭印象勾选。

- 全部满足 → 进入步骤 6。
- 有任何一条不满足 → 视同执行失败：**不勾选、不改标签**，按步骤 3 的格式返回消息，说明哪一条没有满足及原因。

### 步骤 6：全部成功 → 更新 Issue

只有步骤 5 全部满足时才执行，顺序固定：

1. **勾选 checkbox**：把 Issue 正文「验收条件」中全部的 `- [ ]` 改为 `- [x]`，其余正文原样保留，用 REST API 更新正文。
2. **添加标签 `Done`**：仓库中没有 `Done` 标签时先创建（颜色 `0e8a16`，描述「已完成」），再添加。
3. **删除标签 `Todo`**：只删除 `Todo`，保留 Issue 上的其他标签。
4. 更新后重新读取 Issue，确认：checkbox 全部为 `[x]`、含 `Done`、不含 `Todo`。

### 步骤 7：报告

向用户简短报告（不要把生成的文件内容贴回对话）：

- 执行结果：成功 / 跳过 / 失败，以及 Issue 编号。
- 成功时：创建或修改了哪些文件；Issue 上做了哪些更新（checkbox、标签）。
- 执行 skill（如 `readme_generation.md`）要求报告的事项，一并转达。

## 5. 约束

1. 标签只认 `Todo` 与 `Done`，不使用其他名称代替。
2. 状态不明（读取 Issue 失败、API 报错）时，视为前置检查未通过，不执行。
3. 不修改 Issue 的标题、assignee、milestone，不添加评论（除非用户要求）。
4. 不关闭 Issue（除非用户要求）。
5. 不凭猜测补全 Issue 中缺失的信息；有疑问就跳过并询问。
